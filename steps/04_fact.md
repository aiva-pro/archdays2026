# 4. Загрузка факта

Один проход: источник → сбор → распознавание → связь с проектом → репозиторий.

Предусловие: проект сохранён в репозиторий ([03_model.md](03_model.md)). Иначе сопоставлять факт будет не с чем.

До чтения сверки не нажимайте **Привязать всё непривязанное** и **Опубликовать всё готовое**.

## 1. Источник

Работаем на уровне **организации**, не внутри модели. Коннектор читает Docker API стенда, порт `50006`, только чтение, авторизация не нужна.

1. **Интеграции → Источники** (или **Настройки → Интеграции**).
2. На подготовленном стенде источник Docker уже может быть: откройте его и проверьте поля. Если источника нет, нажмите **Добавить источник**.

| Поле | Значение |
| --- | --- |
| Тип | Docker |
| Код | `ECOM_DOCKER` (именно так: к этому коду привязано правило распознавания) |
| Где исполняется | **Облако AIVA**, если стенд доступен по URL; иначе Edge, как скажет ведущий |
| Docker API URL | `http://<хост>:50006` с карточки |
| Unix socket | пусто |
| Что забирать | Containers |

3. Нажмите **Проверить соединение**. При создании: **Создать источник**.

Метки на контейнерах стенда уже стоят: `aiva.system` (ваша система с карточки), `aiva.service`, `aiva.c4`, `aiva.kind`, `aiva.tech`, `aiva.owner`, `aiva.version`, `aiva.port`, `aiva.depends_on`.

Контрольная точка: проверка соединения успешна.

## 2. Сбор

1. **Интеграции → Источники** → ваш коннектор → **Запустить сейчас**.
2. Откройте **Журнал приёма**. Статусы: получено, смаплено, без правила, ошибка.
3. В записях — контейнеры с меткой `aiva.system` вашей команды. Чужие и служебные записи без этой метки не разбираем.
4. Сверьте список с https://ecomarch.aiva-pro.tech/status.

Контрольная точка: записи со стенда приходят, ответ не пустой и не сплошные ошибки.

## 3. Распознавание

Сырая запись Docker ещё не объект модели. Правило раскладывает её в класс `container`. На стенде оно выдано вместе с метамоделью: откройте **Распознавание** и **прочитайте** его. С нуля собирайте, только если ведущий сказал, что правила нет.

| Метка | Поле карточки |
| --- | --- |
| `aiva.service` | имя |
| `aiva.tech` | технология |
| `aiva.owner` | команда |
| `aiva.version` | версия |
| `aiva.port` | порт |
| `aiva.description` | описание |
| `aiva.kind` | тип (`API` или веб-приложение) |

Если нормализованных объектов нет, нажмите **В очередь** или запустите обработку bronze → silver во вкладке **Процессы**.

Контрольная точка: есть нормализованные контейнеры.

## 4. Связь с проектом

Сохранение проекта запускает сопоставление с уже собранным фактом, отдельный ручной прогон не нужен.

1. Откройте **Интеграции → Объекты**.
2. У класса Container виден источник. Совпавшие сервисы связаны с объектами проекта.
3. Фактические значения лежат на обнаруженных объектах. Значения проекта на своих карточках не перезаписываются.

Совпадение по имени ещё не значит совпадение связей и атрибутов: это вы увидите на сверке. Пока только наблюдайте, не принимайте найденное в проект оптом.

Если при сохранении канваса вышло предупреждение о сверке, проект уже записан. Повторно не публикуйте, позовите ведущего.

## 5. Репозиторий

Откройте **Содержимое модели** и убедитесь, что:

- объекты **проекта** на месте (то, что вы сохранили);
- рядом виден **факт** (обнаруженные и сопоставленные записи), и проект ими не переписан.

Если проекта нет, вернитесь к [03_model.md](03_model.md) и сохраните канвас. Если факта нет, вернитесь к шагам 1–3 или позовите ведущего.

Контрольная точка: в репозитории есть и проект, и след загруженного факта.

Дальше: [05_reconcile.md](05_reconcile.md).
